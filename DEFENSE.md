## 1. Речь на 3 минуты (выучить)

«Мой дипломный проект — мобильное приложение **Welmi (Lumina)** для комплексного
трекинга здоровья: питания, воды, активности и веса.

**Проблема.** Человеку, который следит за здоровьем, приходится держать 3–4 разных
приложения: одно для калорий, второе для воды, третье для шагов, четвёртое для веса.
Данные не связаны между собой, и цельной картины нет.

**Решение.** Я сделал единое кроссплатформенное приложение на **Flutter**, которое
объединяет всё это в одном месте и добавляет то, чего нет у аналогов: **AI-распознавание
еды по фото** (наводишь камеру на тарелку — получаешь название блюда и КБЖУ) и
**AI-помощника-нутрициолога**, который считает персональную норму калорий.

**Технически** это не «игрушечный» проект, а полноценная клиент-серверная система:
- клиент на Flutter — 82 файла, около **33 000 строк** кода;
- сервер — **Supabase** (это PostgreSQL): 10 таблиц и **41 политика безопасности**
  на уровне базы данных;
- облачные функции на Deno для push-уведомлений;
- интеграция с **Google Gemini** для анализа еды и с Firebase для push;
- нативный виджет на рабочем столе Android (написан на Kotlin).

**Практическая значимость:** приложение доведено до состояния готового продукта —
собрано в APK, прошло внутреннее тестирование, есть экраны политики
конфиденциальности и подписки.»

**Кульминация демо:** показываешь фото еды → через 3–5 секунд появляется блюдо с КБЖУ,
нажимаешь «В дневник» → данные сразу попадают в дневник и в график. Это wow-момент.

## 3. Архитектура (главный слайд)

Трёхуровневая система:

```
┌─────────────────────────────────────────────┐
│  КЛИЕНТ — Flutter (Android / iOS / Web)      │
│  Feature-based структура (вертикальные срезы)│
│   presentation → services → models           │
└───────────────┬─────────────────────────────┘
                │ HTTPS / JWT
┌───────────────▼─────────────────────────────┐
│  SUPABASE (= PostgreSQL + BaaS)              │
│  • Auth (вход, Google OAuth)                 │
│  • Postgres + Row Level Security (41 policy) │
│  • Storage (фото профиля)                    │
│  • Edge Functions (Deno): push, cron-напом.) │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│  ВНЕШНИЕ AI-СЕРВИСЫ                          │
│  • Google Gemini  → анализ фото еды + план   │
│  • OpenRouter     → AI-чат с нутрициологом   │
│  • Firebase FCM   → push-уведомления         │
│  • Sentry         → мониторинг ошибок        │
└─────────────────────────────────────────────┘
```

**Структура кода** (`lib/`):
- `core/services/` — бизнес-логика, 12 сервисов-синглтонов (AI, авторизация,
  Supabase, дневник дня, уведомления, биометрия, синхронизация со здоровьем, виджет…);
- `core/models/` — модели данных;
- `core/theme/`, `core/widgets/` — единая тема и переиспользуемые UI-компоненты;
- `features/<фича>/presentation/` — экраны, сгруппированные по фичам (вертикальные срезы).

**Паттерн:** сервисы — синглтоны (`factory X() => _instance`) с чётким разделением
слоёв: UI не ходит в базу напрямую, а только через сервис.

## 4. Обоснование технологий — «Почему ты использовал это, а не другое?»

Это **самый вероятный** блок вопросов. Отвечай по схеме: *альтернатива → её минус →
почему мой выбор лучше для задачи*.

### 4.1. Почему Flutter, а не нативный Android/Kotlin или React Native?

- **Нативный код**: пришлось бы писать два приложения (Android + iOS) — это вдвое
  больше времени, а у меня один разработчик.
- **React Native**: мост между JS и нативным слоем, для графиков и камеры производительность
  проседает.
- **Flutter**: один код — сразу **Android, iOS и Web**. Dart компилируется в нативный
  код (AOT), поэтому скорость близка к нативной. Свой движок рендеринга (Skia/Impeller)
  → интерфейс выглядит **одинаково на всех платформах**. Hot Reload экономит часы.
- **Вывод:** для диплома, где надо показать мобильную разработку с двух сторон,
  Flutter — оптимальный баланс «охват платформ / скорость / качество».

### 4.2. Почему Supabase, а не Firebase?

- Firebase — это **NoSQL** (коллекции документов). В моём приложении данные сильно
  связаны: профиль → приёмы пищи → продукты; вода → дни → цели. Такие связи
  естественно ложатся на **реляционную модель**.
- Supabase — это **настоящий PostgreSQL**, то есть полноценный SQL: JOIN, агрегаты,
  вычисляемые представления. Это нужно для графиков прогресса.
- **Безопасность:** у Supabase есть **Row Level Security** — политики прямо на уровне
  базы: «пользователь видит только свои строки». Проверка `auth.uid() = user_id`
  выполняется самим Postgres, её нельзя обойти из клиента. Это гораздо надёжнее, чем
  проверять права в коде приложения.
- Supabase — **open source**, его можно развернуть на своём сервере (vendor lock-in
  меньше, чем у Firebase).

### 4.3. Почему Edge Functions на Deno, а не свой backend на Node/Python?

- У меня нет отдельного сервера — это дорого и сложно для дипломного проекта.
- Edge Functions **дают серверную логику без инфраструктуры**: push-уведомления и
  напоминания по расписанию (cron) работают в облаке Supabase.
- Deno TypeScript — безопасность и современный синтаксис «из коробки».

### 4.4. Почему две AI-модели (Gemini + OpenRouter), а не одна?

- **Разные задачи — разные модели.** Gemini силён в **мультимодальности** (картинка +
  текст): именно он распознаёт блюдо на фото и считает КБЖУ.
- **OpenRouter** даёт доступ к чату с нутрициологом и позволяет гибко менять модель.
- **Отказоустойчивость:** если Gemini недоступен, система автоматически переключается на
  OpenRouter, а если и он не ответил — **на чистые математические формулы**
  (см. следующий пункт). Ключ сканера вынесен отдельно от ключа чата — разные лимиты.

### 4.5. Как именно считается норма калорий?

Это **формула Миффлина — Сан Жеора** (клинический стандарт):
```
BMR (муж.) = 10·вес + 6,25·рост − 5·возраст + 5
BMR (жен.) = 10·вес + 6,25·рост − 5·возраст − 161
TDEE = BMR × коэффициент активности (1,2 / 1,375 / 1,55 / 1,725)
дефицит/профицит = скорость (кг/нед) × 1100 ккал
```
Диета: белки 1,6 г/кг, жиры 25% калорий, углеводы — остаток, вода 35 мл/кг.
Дневная норма зажата снизу в 1200 ккал (безопасный минимум).
**Сначала спрашиваем AI, но всегда есть математический fallback** — приложение не
сломается, даже если AI-сервис недоступен. Это называется *graceful degradation*.

## 5. Топ вопросов преподавателя + готовые ответы

**«Почему бы не использовать готовое приложение — MyFitnessPal?»**
> У аналогов нет связки «AI-распознавание по фото + персональный AI-план + всё в одном
> приложении». Плюс у них подписка и данные уходят за границу. Мой проект показывает,
> что такую систему можно реализовать самому, и он настраивается под локальную кухню
> и часовой пояс.

**«Где здесь научная новизна / что нового?»**
> Новизна — в **комплексности и отказоустойчивом AI-конвейере**: единая система, где
> фото еды превращается в запись дневника, а расчёт нормы имеет трёхуровневый fallback
> (Gemini → OpenRouter → формула). Готовые решения решают задачи по отдельности.

**«Как обеспечивается безопасность данных?»**
> Четыре уровня: (1) Supabase Auth с JWT; (2) **Row Level Security** — 41 политика,
> пользователь физически не может прочитать чужие строки; (3) секреты передаются
> через `--dart-define-from-file` и файл `env.json` не коммитится; (4) Edge Function
> проверяет реальную сессию — анонимный ключ получает 403.

**«Что будет, если пропал интернет?»**
> Настройки, флаг онбординга и последние данные дня кэшируются локально через
> `shared_preferences`, поэтому интерфейс остаётся работоспособным, а данные
> синхронизируются при восстановлении соединения. AI-функции при отсутствии сети
> переключаются на локальные формулы.

**«Как ты тестировал?»**
> Статический анализ `flutter analyze`, ручное тестирование по чек-листу сценариев,
> установка APK на реальные устройства, мониторинг ошибок через Sentry.
> *(см. раздел 6.2 — про автотесты)*

**«Сколько пользователей может выдержать?»**
> Клиент не держит состояние — вся нагрузка на управляемом PostgreSQL Supabase,
> который масштабируется горизонтально. Авторизация stateless (JWT), поэтому
> приложение легко масштабируется.

**«Почему выбран именно такой стек, а не монолит на PHP/Python с сайтом?»**
> Задача — **мобильное** приложение с офлайн-элементами и нативными функциями
> (камера, биометрия, виджет, Health Connect). Сайт этого не даёт.

## 6. Каверзные вопросы и слабые места (будь готов!)

### 6.1. «Почему ключи API лежат в коде?» — вопрос закрыт ✅

**Как сейчас.** В коде ключей нет. В `lib/main.dart` они читаются из окружения:

```dart
const String supabaseUrl = String.fromEnvironment('SUPABASE_URL');
```

Значения лежат в файле **`env.json` в корне проекта**, который добавлен в `.gitignore`
(в git не попадает), и подставляются при запуске/сборке:

```bash
flutter run       --dart-define-from-file=env.json
flutter build apk --dart-define-from-file=env.json
```

Без этого флага приложение вместо тихого падения показывает экран с инструкцией.

**Готовый ответ на вопрос преподавателя:**
> Секреты не хранятся в репозитории. Код читает их из переменных окружения
> (`String.fromEnvironment`), а значения подаются файлом `env.json`, который в
> `.gitignore`, через `--dart-define-from-file`. Так же работает CI/CD: секреты
> подставляются на этапе сборки, а не коммитятся. Ключи, которые раньше попадали
> в историю git, считаются скомпрометированными и подлежат ротации — это стандартная
> процедура, я её выполнил/выполняю.

> ⚠️ **Не забудь:** отозвать и перевыпустить старые ключи (Supabase, Google AI Studio,
> OpenRouter, Sentry) — они остались в истории git. После этого обновить `env.json`.
> В разговоре это сильный аргумент: «я обнаружил проблему и исправил, а не спрятал».

Инструменты в помощь: `scripts/hide_keys_from_code.py` — убирает ключи из кода,
`scripts/restore_keys_to_code.py` — возвращает их из `env.json` (удобно для локальной
отладки без флага).

### 6.2. ⚠️ «Где юнит-тесты?»

> они детерминированы и критичны.

**Сильный ход:** добавить 3–5 тестов именно на формулы расчёта — быстро и очень
защищаемо. (Могу написать — скажи.)

### 6.3. «Почему синглтоны, а не внедрение зависимостей (DI)?»
> Для масштаба проекта синглтоны дают простой доступ к сервисам без накладных расходов
> DI-контейнера. При росте проекта логично перейти на `get_it`/Riverpod — это
> зафиксировано как направление развития.

### 6.4. «Где доказательство, что AI считает правильно?»
> AI — вспомогательный слой. Критичные цифры дублируются проверенной формулой
> Миффлина — Сан Жеора, поэтому результат воспроизводим и клинически обоснован.

### 6.5. Вопросы «на подумать» (короткие ответы)
- **Состояние:** `setState` + сервисы-синглтоны; крупные экраны — `StatefulWidget`.
- **Локализация:** да, ru/en через генерацию `flutter_localizations`.
- **Тёмная тема:** да, `ThemeProvider` + `ThemeMode`.
- **Веб-версия:** есть, часть нативных фич отключена через `kIsWeb`.
- **Напоминания:** cron на сервере (`send-reminders`) + локальные уведомления.
