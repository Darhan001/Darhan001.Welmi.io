## 1. Что это за проект — в одном абзаце

**Welmi (Lumina)** — мобильное приложение для контроля питания, воды, активности и веса.
Пользователь проходит онбординг, приложение считает его норму калорий и БЖУ, а потом
каждый день ведёт дневник: фотографирует еду (нейросеть распознаёт и считает КБЖУ),
отмечает воду, синхронизирует шаги, вносит вес. Все данные лежат в облачной базе
PostgreSQL (Supabase) и защищены политиками доступа. Есть виджет на рабочий стол,
push-напоминания, графики прогресса, тёмная тема и три языка.

                │   └───────────────────┘
                │   ┌───────────────────┐
                │   │ OpenRouter (LLM)  │  ← текстовый AI-чат/советы
                │   └───────────────────┘
                ▼
        ┌────────────────────────────────────┐
        │  Supabase (облако)                 │
        │  • PostgreSQL — база данных        │
        │  • Auth — вход по e-mail/Google    │
        │  • Storage — аватары               │
        │  • Edge Functions — серверный код  │
        └──────────────┬─────────────────────┘
                       │
                       ▼
              ┌──────────────────┐

Главная идея: **приложение не хранит данные у себя, кроме кэша**. Оно спрашивает базу
и показывает ответ. Поэтому данные не потеряются при переустановке.

## 3. Разбор конкретной строки кода

```dart
Text('${_greeting()}, $firstName!',
    style: GoogleFonts.inter(
        fontSize: 18,
        fontWeight: FontWeight.w900,
        color: tc.text)),
```
*(файл `lib/features/home/presentation/pages/home_page.dart`, строка 200)*

### 3.1. Что делает эта строка

Рисует на главном экране надпись вида: **«Доброе утро, Азамат!»**. Слово-приветствие
зависит от текущего времени, имя берётся из профиля пользователя.

### 3.2. По кускам — что означает каждый элемент

| Что написано | Что это значит |
|---|---|
| `Text(...)` | Виджет — элемент интерфейса. «Виджет» во Flutter = любой кусочек экрана: текст, кнопка, отступ. Всё приложение собрано из виджетов как из конструктора. |
| `'...'` | Строка (текст). В Dart строки в одинарных или двойных кавычках. |
| `${_greeting()}` | **Интерполяция строки**: внутрь текста подставляется результат работы метода `_greeting()`. `$` в строке = «подставь сюда значение». `${...}` — когда внутри выражение посложнее, а не просто имя переменной. |
| `_greeting()` | Вызов метода (функции), который определён в этом же классе на строке 81. `_` в начале имени означает «приватный» — доступен только внутри этого файла. Скобки `()` = «вызови и выполни». |
| `,` между ними | Просто запятая в тексте-шаблоне, разделяющая приветствие и имя. |
| `$firstName` | Подстановка переменной `firstName`. Она вычисляется на строке 155: берётся имя из профиля (`displayName`), режется по пробелам и берётся первое слово → «Азамат» из «Азамат Усенов». Если профиля нет — подставляется слово «гость». |
| `!` в конце `'...!'` | Это обычный восклицательный знак в тексте, а не код. |
| `style:` | **Именованный параметр**. У виджета `Text` есть параметр `style` (оформление). Именованные параметры делают код читаемым: видно, что передаётся. |
| `GoogleFonts.inter(...)` | Функция из пакета `google_fonts`. Возвращает объект шрифта **Inter**: при первом запуске шрифт подтягивается из Google Fonts и кэшируется на устройстве. |
| `fontSize: 18` | Размер шрифта в логических пикселях. |
| `fontWeight: FontWeight.w900` | Насыщенность (жирность). `w900` — максимально жирный (Black/Heavy). Есть w100…w900. |
| `color: tc.text` | Цвет текста. `tc` — это `ThemeColors`, полученный выше через `ThemeColors.of(context)` (строка 127). |
| `tc.text` | Геттер, который возвращает **разный цвет для светлой и тёмной темы**: `isDark ? darkText : Colors.black87`. Поэтому при переключении на тёмную тему текст станет светлым без правок этого экрана. |
| `),` в конце | Закрытие вызовов `GoogleFonts.inter(` и `Text(`, запятая — конец параметра. |

### 3.3. Что делает `_greeting()`

```dart
String _greeting() {
  final hour = DateTime.now().hour;                 // текущий час (0–23)
  final loc = AppLocalizations.of(context)!;        // словарь переводов
  if (hour < 5) return loc.greetingNight;           // ночь
  if (hour < 12) return loc.greetingMorning;        // утро
  if (hour < 18) return loc.greetingAfternoon;      // день
  return loc.greetingEvening;                       // вечер
}
```

То есть: берём час → возвращаем строку из **файла переводов** (`AppLocalizations`).
Это и есть локализация: в русском будет «Доброе утро», в английском — «Good morning»,
в кыргызском — свой вариант. Тексты лежат в `.arb`-файлах, из них генерируется Dart-код.
Если бы текст был вписан прямо сюда, приложение не переводилось бы.

### 3.4. «А почему ты сделал именно так, а не иначе?» — 4 готовых ответа

**1. Почему `Text`, а не картинка/Canvas?**
`Text` — базовый виджет: сам переносит строки, подстраивается под размер экрана,
уважает системный размер шрифта (доступность для слабовидящих) и переводится через
локализацию. Рисовать надпись через Canvas пришлось бы делать вручную и мы потеряли
бы всё это.

**2. Почему `GoogleFonts.inter`, а не шрифт из assets?**
Это разовая экономия: пакет сам скачивает нужный шрифт и кэширует его. В репозитории
не лежат файлы шрифтов (меньше вес проекта). Минус — нужен интернет при первом запуске
(в демо это не проблема), а в assets-варианте шрифт был бы всегда локально. Если бы
нуен был 100 % офлайн-первый-запуск, выбрал бы assets.

**3. Почему цвет берётся из `tc.text`, а не `Color(0xFF000000)` напрямую?**
Потому что у нас есть тёмная тема и 3 темы оформления. Один захардкоженный чёрный
цвет в тёмной теме не читался бы. `ThemeColors` — единая точка, где цвет выбирается
в зависимости от темы. Это принцип «единственной ответственности»: экран не решает,
какой цвет правильный, он спрашивает у темы.

**4. Почему приветствие не хранится в состоянии (state), а вычисляется?**
Потому что это **производное** значение: оно зависит только от текущего времени.
Держать его в переменной значит держать в голове синхронизацию (а если пользователь
сидел в приложении с 11:59 до 12:01?). Здесь же есть таймер (`Timer.periodic` каждые
30 секунд в `initState`), который просто перерисовывает экран — и приветствие
становится актуальным само.

## 4. Мини-словарь: как читать Dart-код

| Запись | Значение |
|---|---|
| `final x = 5;` | Переменная, которую нельзя переприсвоить (константа времени выполнения). |
| `x ?? y` | «Если `x` пусто (null), возьми `y`». `displayName ?? 'гость'`. |
| `x!.something` | `!` — «я уверен, что здесь не null», иначе будет ошибка. |
| `x?.something` | «Если `x` null — верни null, не падай». |
| `async` / `await` | «Функция делает что-то долгое (запрос в сеть) и ждёт результат, не блокируя интерфейс». |
| `Future<...>` | Обещание результата, который появится позже (аналог Promise в JS). |
| `setState(() { ... })` | «Данные изменились — перерисуй этот экран». Только внутри `State`. |
| `initState()` / `dispose()` | Жизненный цикл экрана: создался / убирается. В `dispose` освобождаем ресурсы. |
| `StatefulWidget` | Экран, у которого есть изменяемое состояние. `StatelessWidget` — статичный. |
| `=>` | Короткая запись функции: `Color get card => isDark ? A : B;`. |
| `? :` | Тернарный оператор: «если условие — одно, иначе — другое». |
| `class X { ... }` | Класс — описание объекта с его данными (полями) и действиями (методами). |
| `extends ChangeNotifier` | Класс может сообщать «я изменился» тем, кто его слушает (например, `DailyTracker`). |
| `kIsWeb`, `kReleaseMode` | Флаги Flutter: запущено ли в браузере / собрано ли в релиз. |
| `debugPrint` | Печать в лог (только для отладки). |
| `import 'package:...'` | Подключение библиотеки или своего файла. |

## 5. Почему Flutter, а не другое

### 5.1. Почему не нативная разработка (Kotlin для Android + Swift для iOS)

| Критерий | Flutter | Нативно |
|---|---|---|
| Код | Один код на обе платформы | Два разных проекта и двух разработчиков |
| Скорость работы | Компилируется в машинный код (AOT), рисует кадры сам | Максимальная |
| Внешний вид | Одинаковый на Android и iOS | Различается, надо делать два дизайна |
| Доступ к платформе | Есть, через плагины/каналы | Полный и «из коробки» |

**Ключевой аргумент:** у меня нет команды из двух разработчиков и времени писать два
приложения. Flutter дал один код, а когда понадобилась нативная функция (виджет на
рабочий стол), я написал **нативный Kotlin-код и связал его с Flutter через
`home_widget`** — то есть нативность доступна, когда реально нужна
(файл `android/app/src/main/kotlin/com/example/lumina/WelmiWaterWidget.kt`).

### 5.2. Почему не React Native

React Native рисует **нативные компоненты** и общается с ними через мост (JavaScript ⇄
нативный код). У нас много кастомного: кольца прогресса, анимации, градиенты, 3D-модели
мышц. Во Flutter весь интерфейс рисует собственный движок (Skia/Impeller), а не система,
поэтому анимация на 60 fps и одинаковый вид на всех устройствах предсказуемы.
Плюс мост в RN — это сериализация данных на каждый чих, лишние накладные расходы.

### 5.3. Почему не веб-приложение / PWA

Нам нужны камера для сканирования еды, биометрия (отпечаток), виджет на рабочем столе,
Health Connect (шаги), локальные push. Веб-приложение этого не умеет или умеет
ограниченно. Веб-версия у проекта тоже есть, но с отключением нативных функций
(флаги `kIsWeb`).

### 5.4. Почему язык Dart

Он компилируется в **машинный код** (AOT) для релиза — без виртуальной машины в рантайме,
и в JIT для быстрой разработки. Dart изначально заточен под интерфейсы: асинхронность
(`async/await`) встроена в язык, а не приделана библиотекой.

## 6. Почему Supabase, а не Firebase (это спросят почти точно)

| | Firebase (Firestore) | Supabase (PostgreSQL) |
|---|---|---|
| Модель данных | NoSQL: коллекции документов JSON | Реляционная: таблицы, строки, колонки |
| Язык запросов | Свой API, сложные выборки ограничены | Полноценный **SQL**: JOIN, GROUP BY, агрегаты |
| Связи между данными | Вручную (вложенные документы или дублирование) | Настоящие внешние ключи (`FOREIGN KEY`) |
| Права доступа | Security Rules на сервисе | **RLS** — политики прямо в базе, на уровне строк |
| Схема | Гибкая (можно что угодно) | Строгая (`CHECK`, типы, `NOT NULL`) — меньше мусора |
| Аналитика | Нужно выгружать | SQL-запрос прямо по живым данным |

**Главный аргумент — природа наших данных реляционная.** У нас «пользователь → приём
пищи → позиции в приёме»: это классическая связь «один ко многим» с внешними ключами.
В документной базе пришлось бы вкладывать позиции в документ или дублировать данные,
и нельзя было бы сделать «дай сумму калорий за последние 30 дней» одним запросом.

**Второй аргумент — RLS.** Правила доступа описываются в самой базе: «пользователь
видит только строки, где `user_id = его id`». Даже если в клиенте ошибка, база не отдаст
чужие данные. В Firestore аналогичный механизм есть (Security Rules), но он не
подкреплён явными связями между таблицами и целостностью.

**Третий аргумент — не нужно писать свой backend.** Авторизация, база, файлы, REST API
и серверные функции — из коробки (BaaS). Свой backend на Node/Django — это отдельный
сервер, отдельное развёртывание, отдельная безопасность, и всё это на дипломном сроке.

**Честная оговорка для преподавателя (плюс в карму):** если бы проект был про
real-time чат или очень гибкие документы без отношений, Firebase был бы удобнее.
Выбор осознанный, а не «что первое попалось».

## 7. Почему Edge Functions, а не свой сервер

**Задача:** отправить push-напоминание. Для этого нужен **сервисный ключ Firebase**
(service account) — это мастер-ключ, которым можно слать уведомления всем пользователям.

**Почему нельзя положить его в приложение:** APK можно распаковать, ключ украдут.
Значит, ключ должен жить **на сервере**, а приложение просто просит сервер: «отправь
push вот этому пользователю». Ровно это делают Edge Functions `send-push` и
`send-reminders` (файлы в `supabase/functions/`).

**Почему не свой сервер (VPS + Node):** не надо администрировать машину, следить за
обновлениями и платить за простой. Функция запускается только когда её вызывают.
Cron для напоминаний (`send-reminders` каждые 30 минут) настраивается конфигом.
Минус, который стоит назвать самому: привязка к платформе Supabase и «холодный старт»
функции. Для нашего объёма это не проблема.

**Почему функция проверяет сессию:** без проверки любой с anon-ключом мог бы рассылать
push от имени приложения. У нас анонимный запрос получает 403.

## 8. Почему две AI-модели

| Что делает | Модель | Почему она |
|---|---|---|
| Распознаёт **фото еды** и считает КБЖУ | **Google Gemini** (мультимодальная) | Умеет принимать изображение на вход и возвращать структуру — это и есть «мультимодальность» |
| Текстовый чат, советы, подбор плана | **OpenRouter** (LLM) | Единый доступ к разным моделям через один API, дешевле для текста |

Плюс есть **третий слой — обычная формула** (Миффлин — Сан Жеора). Если интернета нет
или AI вернул ошибку, приложение считает норму само. Это называют **fallback**
(запасной путь): логика не ломается никогда.

**Почему AI вообще:** пользователь не хочет взвешивать еду на кухонных весах. Он делает
фото — и получает оценку. Это и есть «новизна практическая»: снижаем порог входа в
трекинг. А критические цифры (норма калорий) всё равно дублируются формулой, чтобы
результат был воспроизводим.

## 9. База данных: как читать схему

### 9.1. Базовые понятия

- **Таблица** — как лист Excel: например, «все взвешивания всех пользователей».
- **Строка (запись)** — один факт: одно взвешивание, один стакан воды.
- **Колонка (поле)** — свойство факта: `weight_kg`, `date`, `user_id`.
- **Первичный ключ (PRIMARY KEY, `id`)** — уникальный номер строки.
- **Внешний ключ (FOREIGN KEY)** — ссылка на строку в другой таблице. Например,
  `food_entries.user_id` ссылается на `profiles.id`: «чей это приём пищи».
- **`CHECK`** — ограничение на значение: «`goal` может быть только из списка».
- **Индекс** — «алфавитный указатель» для быстрого поиска.
- **Миграция / SQL-скрипт** — файл, который создаёт таблицы. У нас — `supabase_schema.sql`.

### 9.2. Зачем 10 таблиц, а не одна большая

Если бы всё писали в одну таблицу, в каждой строке пришлось бы повторять имя
пользователя, дату, тип приёма пищи. Появились бы **аномалии**: изменил профиль —
надо обновить 5000 строк; забыл — данные противоречат друг другу; вместо одного байта
хранишь копию в тысяче мест.

Решение — **нормализация**: каждый факт в своей таблице, а между ними связи по `id`.
Это стандарт проектирования баз данных (правила «нормальных форм»), и именно об этом
спросят: «почему у тебя так много таблиц?» → потому что это третья нормальная форма,
каждый факт хранится один раз.

### 9.3. Зачем `profiles`, если есть `auth.users`

Таблица `auth.users` принадлежит сервису авторизации Supabase: там только e-mail, хэш
пароля, дата регистрации. Добавлять туда свои поля нельзя — её обновления сломают
твой код. Поэтому стандартный приём: **отдельная таблица `profiles`**, у которой
`id` — тот же UUID, что и у пользователя в `auth.users`
(`profiles_id_fkey FOREIGN KEY (id) REFERENCES auth.users(id)`). Один к одному.

`profiles` — самая богатая таблица: цель (`goal`), пол, рост, текущий и целевой вес,
дата рождения (из неё считается возраст для формулы), уровень активности, скорость
цели, тип подписки (`free`/`pro`), система единиц, настройки уведомлений в формате
`jsonb`, даты создания/обновления.

Почему настройки уведомлений в `jsonb`, а не в отдельных колонках: их набор может
меняться, а нам важно простое «включено/выключено» по имени канала. JSON-поле = гибко.

### 9.4. Разбор каждой таблицы

| Таблица | Одна строка = | Зачем она | Почему именно так |
|---|---|---|---|
| `profiles` | один пользователь | все настройки и параметры тела | своей таблицей, потому что `auth.users` менять нельзя |
| `weight_entries` | одно взвешивание (вес + дата) | график прогресса | вес в `profiles` — «текущий», а история взвешиваний нужна для графика. Дублирование осознанное: быстро читать «сейчас» + хранить всю динамику |
| `water_entries` | одна запись воды (`amount_ml`) | прогресс воды за день | храним каждую порцию отдельно, чтобы можно было отменить один стакан и видеть историю, а не только итог |
| `food_entries` | один приём пищи (завтрак/обед/ужин/перекус) за дату | «чек» приёма пищи | тип приёма (`meal_type`) и дата хранятся один раз на приём, а не в каждой еде |
| `meal_items` | один продукт внутри приёма | «строки чека»: «Гречка 150 г — 180 ккал» | связь «один ко многим» через `food_entry_id`. Можно удалить один продукт |
| `activity_logs` | активность за день | шаги, калории, минуты, км | данные приходят из Health Connect; шаги — не одно значение в сутки, а лог |
| `daily_nutrition` | сводка за день | быстрые цифры для главного экрана | агрегат: `UNIQUE(user_id, date)` — одна строка на день. Денормализация ради скорости чтения |
| `body_measurements` | один замер сантиметром (грудь, талия, бёдра, руки, ноги, шея) | динамика объёмов | отдельно от веса: измеряются не всегда и другими инструментами |
| `body_fat_entries` | один замер % жира + метод | контроль состава тела | отдельно от замеров, потому что метод бывает разный (`caliper`, `scale`, `manual`, `estimated`) и не каждый замер тела включает жир |
| `device_tokens` | одно устройство пользователя | push-уведомления | у одного человека телефон + планшет → несколько токенов. Токен обновляется, старые удаляются |

### 9.5. Ключевой вопрос: почему `food_entries` И `meal_items` И `daily_nutrition`

Это самый вероятный вопрос по базе. Отвечай аналогией **«чек из магазина»**:

- **`food_entries` — это чек.** Один приём пищи: дата, тип (завтрак), пользователь,
  суммарные калории.
- **`meal_items` — это строки чека.** Каждый продукт отдельно: название, граммы, КБЖУ.
- **`daily_nutrition` — это дневной отчёт кассы.** Сводка по всем чекам за день:
  всего калорий, белков, жиров, углеводов и воды.

**Почему не всё в одной таблице:** если писать каждый продукт отдельной строкой с
датой и типом приёма, они продублируются у всех продуктов завтрака. Изменил дату —
надо менять в 5 строках. Это нарушение нормализации.

**Почему нужен ещё и `daily_nutrition`, раз есть `meal_items`:** чтобы главный экран
не пересчитывал сумму по десяткам строк при каждом открытии. Это осознанная
**денормализация** — «кэш на уровне базы»: читать быстро, а при изменении дневника
сводка обновляется. Причём `UNIQUE(user_id, date)` гарантирует, что строка на день
ровно одна — двойников не будет.

Если спросят «а не будет ли расхождения между `meal_items` и `daily_nutrition`?» —
честный ответ: источник истины — `meal_items` (детализация), сводка — производная;
при расхождении её можно пересчитать одним запросом. Ещё сильнее было бы делать это
триггером в базе — это назвать как направление развития.

### 9.6. Почему `id` — это UUID, а не число 1, 2, 3

`uuid_generate_v4()` даёт случайный длинный идентификатор вида
`a3f1c9e2-...`. Плюсы: нельзя угадать чужой id и подсмотреть чужие данные перебором;
id можно сгенерировать на клиенте (нужно для офлайн-режима); нет конфликтов при слиянии
данных. Минус: занимает больше места и чуть медленнее индексируется — для нашего
объёма это неважно.

### 9.7. Почему `CHECK` и `ENUM`, а не просто текст

`goal TEXT CHECK (goal = ANY (ARRAY['loseWeight','gainWeight','maintainWeight']))`
означает: в поле можно положить только одно из трёх значений. Попытка вписать
`"похудеть"` вернёт ошибку. Это **защита данных на стороне базы**: мусор не попадёт
даже из кривого кода. `meal_type` — отдельный тип `ENUM` (перечисление), потому что
он используется как полноценный тип и требует жёсткой фиксации вариантов.

### 9.8. Почему есть `created_at` / `updated_at` и триггер

`created_at` — когда строка появилась (аудит и сортировка по времени). `updated_at`
обновляется автоматически **триггером** в базе (`update_updated_at()`), а не кодом
приложения: приложение может забыть, база — нет. Это ещё один пример «правила живут
в базе, а не в клиенте».

### 9.9. Почему `ON DELETE CASCADE`

`user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE` — «если удалить
профиль, удали и все его записи». Иначе после удаления пользователя остались бы
«висячие» строки без владельца. Так же `meal_items.food_entry_id ON DELETE CASCADE`:
удалил приём пищи — удалились и его продукты. Это **целостность данных**.

### 9.10. Почему индексы

`CREATE INDEX idx_weight_entries_user_date ON weight_entries(user_id, date DESC)` —
указатель для поиска. Наш самый частый запрос: «дай записи этого пользователя за
период». Индекс построен именно по этим двум полям и в обратном порядке дат (сначала
свежие). Без индекса база просматривала бы всю таблицу — это называют full scan.

### 9.11. RLS — как это работает простыми словами

**Row Level Security (RLS)** — «безопасность на уровне строк». В базе у каждой таблицы
включается правило, и база сама решает, какие строки видны конкретному пользователю:

```sql
CREATE POLICY "Users can view own weight entries"
  ON weight_entries FOR SELECT
  USING (auth.uid() = user_id);
```

Читается буквально: «пользователь может прочитать строки `weight_entries`, где
`user_id` равен его собственному id (`auth.uid()` из его JWT-токена)».

**Что это даёт:** даже если злоумышленник подсунет чужой id в запрос, база вернёт
пустой результат. Проверка **не в приложении** (которое можно взломать и подменить),
а на сервере базы. Это и есть ответ на вопрос «как защищены данные?»: вход даёт JWT
(Supabase Auth) → каждая таблица закрыта RLS → 41 политика на чтение/добавление/
изменение/удаление по владельцу.

Отдельно можно упомянуть, что RLS в проекте включена на **все** таблицы, включая
измерения тела и токены устройств (это проверялось и исправлялось — хороший аргумент
«я тестировал безопасность»).

## 10. Что происходит при нажатии: ключевые сценарии

### 10.1. Онбординг (первый запуск)

1. Пользователь проходит шаги: пол → рост → вес → цель → скорость → активность.
2. Данные складываются в объект `OnboardingData` (класс с полями и расчётами).
3. Приложение просит AI подобрать норму; если не получилось — считает **сама** по
   формуле Миффлина — Сан Жеора (свойства `bmr`, `tdee`, `dailyCalories`).
4. Результат показывается на экране «план готов» (`calculation_step.dart`).
5. Запись сохраняется в `profiles` (через `SupabaseService`), а флаг «онбординг пройден»
   — локально в `SharedPreferences` (чтобы не спрашивать при каждом запуске).

### 10.2. Сканер еды (главная фишка)

1. Пользователь фотографирует еду (`image_picker`).
2. Фото отправляется в Gemini вместе с промптом: «верни только JSON с КБЖУ».
3. Ответ парсится в объект (`AiService` → `FoodScanResult`), при ошибке — переход
   на запасную модель/подсказку.
4. Данные можно поправить руками и сохранить: создаётся `food_entry` (приём пищи)
   и `meal_items` (позиции).
5. Главный экран пересчитывает прогресс.

**Почему просим модель вернуть именно JSON:** чтобы ответ можно было надёжно
разобрать программно, а не выцарапывать числа из свободного текста.

### 10.3. Дневник и прогресс

`DailyTracker` (синглтон + `ChangeNotifier`) загружает данные дня, складывает калории
по приёмам, сравнивает с целью и **кэширует снимок дня** в `SharedPreferences`.
Экраны построены на `ChangeNotifier`: изменились данные — интерфейс обновился сам.
Прогресс-графики строятся по запросам к `weight_entries` / `activity_logs` за период.

### 10.4. Вода

Кольцо прогресса: сумма `water_entries.amount_ml` за сегодня против цели из профиля.
Быстрые кнопки +250/+500 мл. Тот же расчёт уходит в **нативный виджет Android**
(Kotlin + `home_widget`), а нажатие на виджет открывает приложение по специальной
ссылке `welmi://add_water?ml=250` и добавляет воду.

### 10.5. Push-уведомления

1. Приложение получает от Firebase **FCM-токен** и сохраняет в `device_tokens`.
2. Серверная функция `send-push` берёт токены пользователя и отправляет сообщение
   через FCM HTTP v1 (у неё есть service account, которого нет в приложении).
3. Функция `send-reminders` по расписанию (cron) шлёт напоминания о воде и еде,
   сверяясь с `notification_prefs` из профиля.
4. В payload есть поле `route` (`water`, `diary`, `progress`, `weight`) — приложение
   открывает нужный экран при тапе.

### 10.6. Офлайн

`SharedPreferences` хранит: тему, флаг онбординга, кэш профиля, снимок дня, настройки
уведомлений и биометрии. Поэтому интерфейс не пустой без сети, а AI-функции
переключаются на формулы.

## 11. Формулы, которые надо уметь объяснить

**BMR (базовый метаболизм)** — сколько калорий тело тратит в полном покое
(формула Миффлина — Сан Жеора, признана точнее устаревшей Харриса — Бенедикта):

```
мужчины:  BMR = 10 × вес(кг) + 6,25 × рост(см) − 5 × возраст + 5
женщины:  BMR = 10 × вес(кг) + 6,25 × рост(см) − 5 × возраст − 161
```

**TDEE (суточная потребность)** = BMR × коэффициент активности:

| Уровень | Коэффициент |
|---|---|
| сидячий (`sedentary`) | 1,2 |
| лёгкая активность (`light`) | 1,375 |
| средняя (`moderate`) | 1,55 |
| высокая (`high`) | 1,725 |

**Целевая норма калорий** = TDEE ± дефицит. Дефицит берётся из скорости цели:
`goal_speed_kg_per_week × 1100` ккал, и для похудения норма «зажимается» снизу
на 1200 ккал (безопасный минимум) через `.clamp(1200, tdee)`.

**БЖУ:** белок = 1,6 г на кг веса; жир = 25 % калорий ÷ 9 (в 1 г жира 9 ккал);
углеводы = остаток калорий ÷ 4 (в 1 г углеводов и белка 4 ккал).

**Где это в коде:** `lib/core/models/supabase_models.dart` и
`lib/core/models/onboarding_data.dart` (геттеры `bmr`, `tdee`, `dailyCalories`,
`proteinGrams`, `fatGrams`, `carbGrams`), а также запасной расчёт в
`lib/core/services/ai_service.dart`.

## 12. Вопросы преподавателя и короткие ответы

**«Почему Flutter?»** — один код на Android и iOS, собственный движок рендеринга,
нативные функции доступны через плагины (виджет написан на Kotlin).

**«Почему Supabase, а не Firebase?»** — данные реляционные (пользователь → приёмы →
позиции), нужен SQL и агрегаты, и нужна защита на уровне строк (RLS). Плюс не надо
свой backend.

**«Что такое RLS?»** — правила в базе: `auth.uid() = user_id`. Даже с чужим id в
запросе база вернёт пусто.

**«Зачем столько таблиц?»** — нормализация: каждый факт хранится один раз, связи по
внешним ключам, нет дублирования и аномалий обновления.

**«Почему отдельно `food_entries` и `meal_items`?»** — чек и строки чека: приём пищи
один раз хранит дату и тип, а продукты — отдельные строки, связанные `food_entry_id`.

**«Зачем `daily_nutrition`, если есть детализация?»** — денормализованный кэш сводки за
день, чтобы главный экран не считал сумму каждый раз. `UNIQUE(user_id, date)`.

**«Почему UUID?»** — нельзя угадать чужие id, можно генерировать на клиенте, нет
конфликтов.

**«Что если база «упадёт»?»** — Supabase на управляемом PostgreSQL с резервными
копиями; клиент держит локальный кэш и работает с ним.

**«Что если нет интернета?»** — кэш в `SharedPreferences`, AI откатывается на формулы,
записи синхронизируются при появлении сети.

**«Как проверяли безопасность?»** — вход по JWT, RLS на всех таблицах (41 политика),
секреты в переменных окружения, серверные функции проверяют сессию и отдают 403
анонимному ключу.

**«Где серверный код?»** — `supabase/functions/send-push` и `send-reminders`
(Deno/TypeScript), они держат секретный ключ FCM и cron.

**«Как тестировали?»** — `flutter analyze` (статический анализ), ручные сценарии на
реальных устройствах, мониторинг ошибок через Sentry. Автотесты — в планах, приоритет:
чистые формулы расчёта.

**«Сколько это выдержит пользователей?»** — клиент без состояния, авторизация
stateless (JWT), вся нагрузка на масштабируемый PostgreSQL.

**«Почему синглтоны, а не DI?»** — меньше накладных расходов на данном масштабе;
при росте логично перейти на `get_it`/Riverpod.

**«Как работает локализация?»** — `.arb`-файлы (ru/en/ky) → генерация `AppLocalizations`
→ все тексты берутся по ключам, а не вписаны в код.

**«Откуда берутся шаги?»** — Android Health Connect через пакет `health`, синхронизация
в `activity_logs`.

**«Почему виджет нативный, а не Flutter?»** — виджеты на рабочем столе Android —
системная функция, Flutter туда не рисует. Написан на Kotlin, данные передаются через
`home_widget`.

## 13. Слабые места и как отвечать честно

**1. Секреты.** Ключи раньше лежали в `lib/main.dart` как `defaultValue` и попали в
историю git. Сейчас они убраны из кода и живут только в `env.json` (файл в
`.gitignore`). Всё, что было в истории, всё равно считается скомпрометированным —
такие ключи нужно отозвать и перевыпустить.

> Формулировка: «Я нашёл это при ревизии и исправил: секреты читаются из окружения
> через `--dart-define-from-file`, файл с ключами не коммитится. Ключи, попавшие в
> историю, подлежат отзыву — это стандартная процедура ротации секретов».

**2. Автотесты.** Папка `test/` пустая. Ответ: упор был на функциональность; приоритет
покрытия — детерминированные функции (BMR/TDEE/БЖУ, норма воды), потому что их
результат можно проверить точно.

**3. Агрегат `daily_nutrition`** обновляется приложением, а не триггером базы —
назвать как направление развития (перенести пересчёт в базу).

**4. Состояние** — `setState` + сервисы-синглтоны. Для проекта такого размера ок;
при росте — DI и менеджер состояния.
